**Document Version:** 1.0.0  
**Status:** Approved for Review  
**Date:** 2026-11-12

## 1. Decision: UUIDv4 as Primary Key Across All Tables

### Context
Traditional auto-incrementing integers (`BIGSERIAL`) leak operational velocity (e.g. total documents uploaded or total registered users), are susceptible to enumeration/BOLA attacks in REST endpoints, and cause merge conflicts if migrating or importing data between test and production environments.

### Decision
All tables use UUIDv4 (`UUID` type in PostgreSQL, generated by `gen_random_uuid()` or Python `uuid.uuid4()`).

### Consequences & Trade-offs
- **Pros:** Completely non-enumerable, collision-free, distributed generation without database roundtrips, secure against IDOR guessing.
- **Cons:** 16-byte storage vs 8-byte `BIGINT`, slight fragmentation in standard B-tree indexes compared to sequential integers. Mitigated because transaction volume in MVP is well within Postgres in-memory cache capacity.

## 2. Decision: Hybrid Relational-JSONB Storage Strategy

### Context
Document intelligence extracts variable structured models (different policies have different clauses, approval tables, and annexures). Normalizing every extracted clause into a relational schema produces dozens of sparse tables with expensive join queries. Conversely, storing everything as a single JSON blob destroys queryability, referential integrity, and indexing.

### Decision
Adopt a strict **Hybrid Schema**:
- **Relational Entities:** Fixed governance structures (`users`, `documents`, `analysis_runs`, `compliance_rules`, `findings`, `review_tasks`, `audit_events`) are strictly normalized tables with hard SQL constraints, foreign keys, and indexes.
- **JSONB Fields:** Used exclusively for variable or telemetry data:
  - `document_extractions.metadata`: Raw bounding boxes and character offsets.
  - `analysis_steps.input_metadata` & `output_metadata`: Step observations and tool arguments.
  - `extracted_items.extracted_value`: Dynamic entity fields parsed by Pydantic.
  - `compliance_rules.rule_definition`: Declarative condition expression tree.
  - `findings.evidence`: Verbatim quotes and page references.

## 3. Decision: Soft Delete for Documents, Hard Delete for Transient Data

### Context
If a user deletes a document, deleting it outright (`CASCADE`) would destroy historical audit trails, invalidate past `analysis_runs`, and break compliance reports for previously completed reviews.

### Decision
1. **`documents` Table:** Uses soft deletion via `deleted_at TIMESTAMPTZ NULL`. The file record is excluded from normal listing queries (`WHERE deleted_at IS NULL`), but retained in the database to support audit reproducibility. Physical disk removal is scheduled or handled according to retention policies.
2. **`refresh_sessions` Table:** Soft revocation via `revoked_at TIMESTAMPTZ NULL` to detect session hijacking / token replay attempts.
3. **Transient Data:** Cache records or ephemeral test runs can be hard-deleted during scheduled maintenance.

## 4. Decision: Foreign Key Cascade Restraints on Governance Records

### Context
In automated systems, careless `ON DELETE CASCADE` rules can silently obliterate historical audit events or review decisions when a parent record is deleted.

### Decision
Strictly differentiate Cascade behaviors:
- **`ON DELETE CASCADE` Permitted Only For:**
  - `refresh_sessions` $\to$ `users` (erasing sessions of a deleted account).
  - `document_extractions` $\to$ `documents` (purging raw text cache if parent document is purged).
  - `analysis_steps` $\to$ `analysis_runs` (telemetry tied to run lifecycle).
  - `extracted_items` $\to$ `analysis_runs` (extracted items tied to run lifecycle).
- **`ON DELETE RESTRICT` Enforced On:**
  - `documents` $\to$ `users` (cannot delete user with active documents).
  - `analysis_runs` $\to$ `documents` (cannot delete document with existing compliance analysis history).
  - `findings` $\to$ `analysis_runs` (cannot delete analysis run with generated findings).
  - `review_tasks` $\to$ `findings` (cannot delete finding with an active or historical review task).
- **`ON DELETE SET NULL` Enforced On:**
  - `audit_events` $\to$ `users` (if user account is purged under privacy laws, historical audit record remains with `actor_id = NULL` and sanitized actor summary in metadata).
  - `findings` $\to$ `compliance_rules` (if a compliance rule is retired, findings evaluated against it retain their provenance).

## 5. Decision: Single PostgreSQL Database (No Redis / No Vector DB in MVP)

### Context
Modern AI stacks frequently introduce Redis for caching, Celery for tasks, and Chroma/Pinecone/pgvector for embeddings. For the MVP, this introduces immense DevOps complexity, distributed state failures, and maintenance burden.

### Decision
PostgreSQL 15+ is the **sole state store**.
- Text search for evidence retrieval uses PostgreSQL native full-text search (`to_tsvector` / ILIKE) and page offset matching.
- Document extraction and agent loops run synchronously or via lightweight FastAPI background tasks.
- Background task queues (Celery/Redis) and vector databases are deferred until post-MVP milestones when scale warrants them.
